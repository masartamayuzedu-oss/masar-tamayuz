# مسار التميز — النسخة المصححة

## التشغيل

يتطلب Node.js 18 أو أحدث.

```bash
npm install
npm start
```

الإعداد الافتراضي يستخدم `serve` لتقديم الملفات الثابتة. يمكن تشغيل الخادم البديل مباشرةً:

```bash
node server.js
```

يستمع الخادم إلى `PORT` أو المنفذ `10000` افتراضياً.

## محتويات المشروع

- `index.html`: الصفحة الرئيسية ولوحة الإدارة.
- `من-نحن.html`: صفحة من نحن.
- `server.js`: خادم ملفات ثابتة بديل مع حماية مسارات وMIME للوسائط.
- `supabase/migrations/202611190001_security_and_compatibility.sql`: ترحيل أمني وتوافقي؛ راجعه ثم نفذه يدوياً.
- `supabase/functions/get-media-view-url/index.ts`: Edge Function لإصدار روابط عرض مؤقتة للوسائط المنشورة.
- `supabase/config.toml`: تعطيل تحقق JWT على مستوى البوابة لهذه الوظيفة العامة فقط؛ الوظيفة تتحقق من وجود السجل المنشور ومسار الملف قبل إصدار الرابط.

## إعداد Supabase

تستخدم الواجهة Project URL ومفتاح `sb_publishable_` العام المضمنين في الواجهة. لا تضع `service_role` أو أي سر داخل HTML أو JavaScript.

الجداول المستخدمة:
- `services`
- `offers`
- `portfolio_items`
- `platform_settings`
- `admin_users`
- `site_headings_config`

حاويات التخزين:
- `masar-media`: عامة لصور المحتوى فقط (JPEG/PNG/WEBP/GIF). تنبيه: الروابط العامة المباشرة لا تخضع لـ RLS؛ إخفاء سجل غير منشور لا يبطل رابط صورته إذا كان معروفاً. انظر التقرير قبل اعتبار ملفات الصور غير المنشورة خاصة.
- `masar-private-media`: خاصة لفيديوهات وملفات PDF التي تُعرض بروابط مؤقتة.

### تطبيق الترحيل

1. خذ نسخة احتياطية من قاعدة البيانات قبل أي تغيير.
2. افتح ملف SQL وراجعه مقابل المخطط الحالي.
3. نفّذه يدوياً في Supabase SQL Editor أو عبر آلية migrations المعتمدة.
4. لا يحذف الترحيل أي جدول أو بيانات. يضيف `services.is_published` افتراضياً `true` ويضبط مولدات IDs للجداول التي أظهر التقرير أن معرفاتها بلا default.
5. تحقق من نتيجة كل أمر، ثم اختبر حساب المدير والقراءة العامة.

### نشر Edge Function

انشر مجلد `supabase/functions/get-media-view-url` باسم `get-media-view-url`. تأكد من ضبط الأسرار التالية في بيئة Supabase Functions:
- `SUPABASE_URL`
- `SUPABASE_SERVICE_ROLE_KEY`

لا تنسخ المفتاح السري إلى ملفات الواجهة. إعداد `verify_jwt = false` مقصود حتى يستطيع الزائر مشاهدة الوسائط المنشورة دون تسجيل دخول؛ لذلك تعتمد حماية البيانات على تحقق الوظيفة من القسم والمعرف والنشر ونوع الملف والمسار، وليس على CORS أو JWT.

تُصدر الوظيفة Signed URL صالحة لمدة 300 ثانية. يوجد حد محاولات محلي best-effort لكل نسخة تشغيل؛ يجب ضبط rate limiting إضافي على مستوى البوابة/WAF إذا تطلب الاستخدام حماية موزعة ثابتة.

## حدود رفع الملفات

أظهر تقرير Supabase أن الحد الأقصى لكلتا الحاويتين هو 100 MiB. تمت مواءمة تحقق الواجهة مع 100 MiB. لا ترفع الحد إلا بعد التحقق من حد المشروع وإعدادات الحاوية؛ تجاوز حد Storage سيُرفض من الخادم حتى لو قبلته الواجهة.

الأنواع المدرجة في التقرير:
- الصور: JPEG وPNG وWEBP وGIF.
- الفيديو: MP4 وWEBM.
- PDF: `application/pdf`.

## صلاحيات الإدارة

تسجيل الدخول يتم عبر Supabase Auth، ثم يتحقق الموقع من وجود UID الحالي في `admin_users`. لا يكفي إخفاء عناصر الواجهة؛ سياسات RLS هي الحاجز الفعلي لعمليات الكتابة. احتفظ بإضافة المديرين وإزالتهم من خلال إجراء إداري موثوق فقط.

## اختبارات بعد النشر

الاختبارات المحلية لا تستطيع إثبات صحة إعدادات مشروع Supabase الحقيقي. بعد تطبيق الترحيل ونشر الوظيفة، اختبر على مشروع staging أو بحسابات anon/admin منفصلة:
- قراءة السجلات المنشورة فقط.
- رفض قراءة غير المنشور من anon.
- رفض INSERT/UPDATE/DELETE من anon.
- السماح للمشرف المصرح له بالعمليات الإدارية.
- مشاهدة صورة عامة ووسيط خاص منشور دون جلسة.
- رفض وسيط غير منشور أو مسار غير مطابق.
